# 0012 Signed commits from the web editor

## Status

Accepted.

## Context

The web editor (ADR 0007) commits through the GitHub App's installation token, with the author's name and email on the commit and a `Co-authored-by` trailer. Those commits are unsigned, so GitHub does not show them as Verified, and a repository whose branch protection or rulesets require signed commits refuses them outright. Many organisations turn that rule on.

The product owner decided:

- Authors who sign in to the editor with GitHub commit as themselves, with their own GitHub user access token, so GitHub attributes and signs the commits.
- Where the base branch or the author's branch requires signed commits, authors without a GitHub token (company OIDC sign-in, including managed hosting) cannot save or publish. The editor says so and offers **Sign in with GitHub**. There is no fallback where the app signs for them.
- Repositories without the requirement keep working for everyone. Authors with a GitHub token still commit as themselves, so their commits are Verified.
- GitHub makes the publish merge. The step that merges `main` into the author's branch must also produce signed commits on repositories that require them.

## Research: which GitHub API paths produce signed commits

Checked against GitHub's documentation in October 2026.

| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- |
| GraphQL `createCommitOnBranch`                           | **Yes.** "Commits made using this mutation are automatically signed by GitHub if supported and will be marked as verified in the user interface." The commit "will be authored by the owner of the credential which authenticates the API request. The committer will be identical to that of commits authored using the web interface". Author and committer cannot be set. It "creates a commit whose parent is the HEAD of the provided branch and also updates that branch", and `expectedHeadOid` (required) is "the git commit oid expected at the head of the branch prior to the commit". The editor's app path sets the author, so its commits are unsigned. ## Decision

**Who commits.** On GitHub sign-in with a GitHub App's client credentials (the app connected in the admin console, or `GITHUB_OAUTH_CLIENT_ID` starting with `Iv`), the editor keeps the author's user access token and refresh token, sealed, and makes all of that author's writes with it: branch creation, commits, pull requests, merges. OAuth App credentials are not used for this: they would need the broad `repo` scope, so their tokens are still used once at sign-in and discarded, as before. Authors without a token commit through the app as before.

**Saves through `createCommitOnBranch`.** A save is one GraphQL mutation with the files as base64 additions and `expectedHeadOid` set to the head the editor read. A mismatch (`STALE_DATA`) becomes the existing "changed since you opened it" refusal, so the mutation also gives the optimistic concurrency the old `PATCH /git/refs` fast-forward check did. The commit message is the author's note plus "Saved in the OpenD web editor."; no trailer is needed, since GitHub authors the commit as the user.

**Signing requirement.** The editor reads classic protection (`required_signatures`) and rulesets for both the base branch and the author's working branch (its real name, or `editor/<user-id>/new` before it exists, so a ruleset on `editor/**` counts). Any `true` means `required`; any 403 means `unknown`; otherwise `not-required`. Results are cached for a minute per repository and branch.

| Requirement    | Author with a GitHub token                     | Author without one (OIDC, managed hosting) |
| -------------- | ---------------------------------------------- | ------------------------------------------ |
| `required`     | Signed flow                                    | Refused before any GitHub write (403)      |
| `unknown`      | Signed flow (safe either way)                  | App path, as before (never blocked)        |
| `not-required` | `createCommitOnBranch` saves; merges as before | App path, as before                        |

**The signed flow: merging `main` without an unsigned commit.** `createCommitOnBranch` cannot make merge commits, and `POST /merges` is not documented to be signed, so on repositories that may require signatures `main` is merged in only by GitHub's `update-branch`, which needs the branch's pull request:

- Opening a page or saving merges `main` in only when the branch has an open pull request. Before that, the branch simply stays behind (the editor says "main has newer changes; GitHub merges them into your branch when you publish") and conflicts are still detected, read-only, from the three trees.
- **Publish** opens (or updates) the pull request as the author, marks a draft ready, then merges `main` in through update-branch if the branch is behind, then squash-merges at exactly that head. GitHub signs both merges.
- **Conflict resolution** cannot be a two-parent commit of the author's choosing, so it is three steps, all signed: (1) a `createCommitOnBranch` commit that sets every file changed on both sides to main's version, so GitHub's merge has nothing left to conflict on; (2) update-branch, which merges main in (if the branch has no pull request yet, the editor opens one **as a draft**, saying why); (3) a `createCommitOnBranch` commit that writes the author's choices (theirs needs nothing, mine or hand-edited text) and any line-by-line merges back. The result has main as an ancestor and the author's resolution as its content, exactly like the old merge commit. The same three steps handle files that only `merge3` can merge line by line. Each step is checked against the expected head; a race gives "Something changed while merging".
- update-branch is asynchronous: the editor polls the branch head for a few seconds and says "GitHub is still merging" if it has not moved.

Trade-offs of the signed flow: the branch history shows an extra "take main's version" commit per resolution (squash-merging keeps `main` tidy); resolving conflicts before publishing opens a visible draft pull request; previews of a branch without a pull request do not include main's newest changes until publish; publish validates the branch before main is merged in (as before, main itself was validated by its own build).

**Refusal and UI.** `SIGNED_COMMITS_REQUIRED`: "This repository requires signed commits. Sign in with GitHub to save and publish." It is thrown by save, new topic, conflict resolution, publish and escalate before any GitHub write; page views (which used to merge `main` in) only read. Pages show the commit identity ("Commits as @login — Verified by GitHub", or "Commits as the OpenD app on your behalf"), a "Signed commits required" badge, and, when blocked, an alert with **Sign in with GitHub** (only when GitHub sign-in can keep a token), the Save, Create topic, Save my choices and Publish buttons disabled. JSON refusals carry `signInUrl`, which the editor script turns into a link. Signing in with GitHub from a company-sign-in session ends that session.

**Token storage.** Migration `008_editor_github_tokens`: one row per editor session (`on delete cascade` from `editor_sessions` and `editor_users`), with the access and refresh tokens sealed by the settings `SecretBox` (ADR 0011: the same `OPEND_SECRET_KEY` or `SESSION_SECRET`-derived key), the associated data binding each ciphertext to its session id, and `expires_at` / `refresh_expires_at`. A row only opens for a live session (not expired, not revoked, author not disabled). Tokens are refreshed five minutes before they expire, under a Postgres advisory lock per session so two replicas never spend one refresh token twice. Sign-out, session revocation and `disable-user` delete the rows; expired sessions' rows are purged at the next GitHub sign-in; a row the key cannot open is deleted (the author signs in again). Without a secret key no token is kept and the editor logs a warning. Tokens never appear in responses, logs, audit details or the browser: `GitHubSignIn.grant` is not enumerable, and the tests scan every response, log line and audit row for every token the fake issued.

**Errors.** A 401 from GitHub (revoked token) or a failed refresh deletes the token and answers "Your GitHub sign-in has expired or was revoked. Sign in with GitHub again to save and publish." A 403/404 on a write, or a GraphQL `FORBIDDEN`/`NOT_FOUND`, answers "GitHub does not let @login write to owner/repo. Ask a maintainer of the repository for write access, then try again."

**Managed hosting.** In token-broker mode the editor's author sign-in is OIDC against the control plane, which gives the editor no GitHub user token. Signed-commit repositories therefore refuse those authors with the same message; the alert explains that company sign-in through managed hosting does not carry a GitHub identity. A connected app with client credentials (GitHub sign-in) still works alongside the broker.

## Consequences

- GitHub-signed-in authors' commits are Verified everywhere, and attributed to their GitHub account rather than to the app.
- Repositories that require signed commits work with the editor for GitHub authors; company-sign-in authors there need a GitHub account.
- The GitHub App's existing permissions (Contents, Pull requests: write; Administration: read) cover the user-token path, since a user token is limited to the app's permissions. **Expire user authorization tokens** may stay on (the default); the editor refreshes.
- `FakeGitHub` gained GraphQL `createCommitOnBranch` and `markPullRequestReadyForReview`, update-branch, draft pull requests, `required_signatures`, rulesets on patterns, user tokens with expiry, refresh and revocation, per-user permissions, and enforcement: unsigned new commits are refused on branches that require signatures, and squash merges are blocked by unsigned head commits, as on GitHub. `POST /merges` makes unsigned commits in the fake, the conservative reading of [7].

## Risks and follow-ups

- **update-branch signing is not stated in its REST reference.** We rely on it being the **Update branch** web action, which GitHub signs. If a repository rejects it, the editor shows GitHub's refusal and nothing is lost; a fallback would be to read `verification.verified` of the merge (`GET /commits/{sha}`) and tell the author to ask a maintainer to update the branch. Verify against a real repository with `required_signatures` before rolling out widely.
- **Managed hosting:** the control plane could issue GitHub user tokens through a token-exchange endpoint (OIDC session → GitHub App user token for the same person), letting OIDC-signed-in authors commit as themselves. Not implemented.
- Tokens are not revoked at GitHub on sign-out (`DELETE /applications/{client_id}/token`); they are deleted locally and expire within eight hours.
- Rotating `SESSION_SECRET` without `OPEND_SECRET_KEY` makes stored tokens unreadable; authors are asked to sign in with GitHub again.
- `createCommitOnBranch` sends file contents base64-encoded in one request; very large maps or topics are bounded by the editor's 2 MB request limit.
