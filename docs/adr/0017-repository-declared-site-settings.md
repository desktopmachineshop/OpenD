# 0017 Repository-declared site settings and auto-connect

## Status

Accepted. Supersedes the clause of ADR 0010 that "nothing in the docs repository may widen who sees what" for the settings listed here, and the "operator-controlled" wording of ADRs 0010 and 0016.

## Context

Setting up a hosted site took a person in the admin console after the GitHub App was installed: pick the repository, type its docs folder and release refs, choose access and public entitlements, the version picker and release lines. On OpenV's shared tenant that was a list of console fields or admin API calls for every new site, and the values already lived in the docs repository's own conventions (`manual/`, `docs/<minor>` branches, public free-plan docs). The maintainer's rule: once a site exists and its owner installs the GitHub App on the docs repository, nobody should fill in anything. The repository declares how the site is set up, and OpenD applies it.

## Decision

**A `site:` block in `opend.config.yaml`.** `siteSettingsSchema` in `@opend/model` takes the admin API's names and values, all optional: `releaseRefs`, `releaseLines`, `access`, `publicEntitlements` (version may be `latest`) and `versionPicker` (including `live`). The schemas for entitlements, the public set and the picker moved from the server to `@opend/model`, so the admin API, the console, seed files and the config validate with one definition. The block is strict (an unknown field is an error), and the public set may only name products and features declared under `attributes`. Problems are `invalid-config` diagnostics naming the field, so `opend validate --strict` catches them in CI.

**Which build speaks for the site.** The build that goes live on the repo's newest release line (by version, `0.23` above `0.3`) applies its block. Builds of older lines (a backport to `docs/0.22`) and builds that a newer push already superseded change nothing. We considered "the newest build of the default branch", but OpenV's default branch is not a release ref and is never built; the newest live line is the version readers are served by default (`latest`), every release branch carries the block, and a backport can never roll the settings back to an older branch's. The block applies in the publishing transaction (`PublishInput.onLive`, with the repo row locked for update), so no reader is served a new release under the old settings, and through the same store calls and audit actions as the admin API (`changeReleaseLines`, `setRepoAccess`, `setRepoVersionPicker`, `setRepoReleaseRefs`), audited as `repo:opend.config.yaml` with the ref and sha. A failure is rolled back to a savepoint and logged: the release still goes live, and the next build retries.

**Declared fields are the repository's.** Migration `013_declared_site_settings` adds `repos.site_settings` (`{settings, ref, sha, release, appliedAt}`), returned as `declared`. The console shows those fields as "Set by opend.config.yaml" with disabled inputs and no save button, and its handlers keep the stored value for them whatever is posted; the admin API answers 409 to a change; a seed file leaves them; re-registering the same repository and folder keeps declared release refs. Fields the block leaves out stay console-managed. Removing the block hands the settings back with their last values. Changing the site's repository or docs folder clears the record.

**Never leaking.** The block only sets the same columns the admin API sets, so the delivery path, its filters and cache keys are unchanged: switching to public opens exactly the public set (fail-closed without one), and every setter notifies `release_changed`, so every replica drops its views, pages and site cache. Tests build a repository that switches public and back and check every leak marker and the cached pages on both sides.

**Auto-connect.** With no docs source and a GitHub App that exposes exactly one repository (the stored installation's list, or the broker's `GET /repos`), `autoConnect` reads the default branch through the git data API, takes the root `opend.config.yaml`, else the only one up to three folders down (not in hidden folders or `node_modules`), else the only one with a `site:` block, registers the repository with that folder and `site.releaseRefs` (default: the default branch), and queues every release ref's head, through the same `saveSource` and `queueReleaseBuilds` as the console's Docs source form and Rebuild now. A Postgres advisory lock and a recheck make concurrent attempts connect once. It runs where an installation completes (`/admin/github/installed` in stored mode, the provider's return to `/admin/integrations?github=connected` in broker mode), lazily on the console's Overview and Docs source pages, after a push from a repository the site does not serve, and before each poll of a polling worker. Several repositories, several candidate folders, an invalid block or an unreadable repository leave it to the picker, and the Overview says why; that outcome is reused for a minute so page views do not call GitHub each time.

## Consequences

- Whoever can push to a release ref can now make the site public, which before took a staff reader. That person could already publish any content to every registered reader, and the change is audited with its commit; branch protection (required reviews) on the release refs is the control. There is no server switch to ignore the block; one can be added if an operator needs the old split.
- The managed fleet worker does not poll, so in broker mode a site that nobody visits after the install is connected on the provider's return page, on the first console visit, or on the first forwarded push.
- Release refs a changed block newly matches build on their next push (or poll); nothing lists remote refs at publish time.
- One schema serves the admin API, the console, seed files and the config, so a new picker mode or access value reaches all four together.
